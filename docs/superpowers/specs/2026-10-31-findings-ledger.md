# Findings Ledger

**Purpose:** the one place to check before trusting a claim about this project. Each entry says how it was checked. Older docs stay as history; where they disagree with this file, this file wins.
**Last checked:** 2026-11-01.

**How to read the status:**
- **Verified:** checked directly against code, git or GitHub, on the date above.
- **Corrected:** an older doc or a repeated assumption turned out to be wrong.
- **Disputed:** our docs disagree and nothing has settled it.
- **Untested:** plausible, but never run on hardware.

## Technical limits

| Claim | Status | Evidence |
|---|---|---|
| Draw order isn't distance. | Verified as a limit | Priorities are compositing data. Street Fighter II paints floor and sky into one layer, so no slot can separate them. RAM-keyed profiles can pick depth per scene, not invent layers. |
| Pixels hidden in the source frame can't be recovered by depth alone. | Verified as a limit | Gap fill invents strips from neighbouring tiles, and it only covers a background's own priority split. |
| Windows and colour-math regions stay in screen space. | Verified as a limit on the 3DS path; **reported fixable on libretro** | rcmz's `KNOWN_ISSUES.md`. Sub-screen effects can land at the wrong depth. The RetroArch session reports shifting a per-eye clip table per BG layer and OBJ priority (libretro `8964837`, local only): rigid-shift exact samples rose from 1152 to 1420 of 1502. Its traps: edges within 8 px of a screen side must stay fixed, because SMRPG masks outer columns with a window; sprite windows must keep screen edges fixed, or sprites draw at negative x (it crashed KSS); the backdrop has no slot, and using BG1 p0 for it is a guess. Mode 7 lines and Star Fox mode 2 bands aren't fixed. Not ported to or tested on the 3DS. |
| Recomps are achieving more precise 3D. | **Corrected: yes, for one game** | `tinaut1986/sm-3ds` has a custom renderer, game-state screen rules and a 4,322-line hand table of per-room and per-tile planes. It's a C port of one game, not an emulator feature. Docs read and code searched, not audited. One README says the hand table isn't wired in, so verify before citing it. SuperMetroidRecomp mentions no depth in what we found. |
| Precise depth on every ROM can be automated. | **Corrected: not feasible** | Priority is compositing order ([nesdev](https://snes.nesdev.org/wiki/Backgrounds)), and the same slot means different things per game or room. Zelda's scene at `$0010`=07/0E has no BG1 on the main screen at all. sm-3ds records that rules inferring depth from level data broke things. Precision needs per-game data. |
| The sub screen is mono by architecture. | **Corrected: old pipeline only** | True of our May release ("Draw sub-screen layers once"). The merged rcmz base redraws sub then main on each eye pass, from code reading; not run, and GPU cost unmeasured on 3DS. On libretro a shared sub garbled DKC's mode 5 logo and per-eye was clean; Yoshi's Island sampled frames showed no difference. |
| Reading `PPU.BG3Priority` at draw time is reliable. | **Corrected** | It reads end-of-frame in the May release. On libretro, an SMW level has BG3 priority on for y=0-36 and off below, so that read returns off. The merged base records slot sources while sections render, which should be band-correct; not run. |
| Mario has one sprite priority. | **Reported: differs by scene** | On libretro: priority 2 in a level (frame 1800), priority 3 on the map (frame 2200). One frame each. |
| Sprites can follow the Mode 7 ground. | Recorded from Jorge's fork | Built, then removed on 2026-09-25: depth snapped and composite sprites pulled apart. Don't retry without a new idea. |
| The console is the only way to run a build. | **Corrected** | Azahar is installed at `C:\Program Files\Azahar`. It can catch boot and logic faults but can't judge how the 3D looks. The fork's test script is Linux-only. |
| Azahar garbles this renderer. | **Reported cause; test patch only** | RetroArch session: the tile geometry shader writes `outpos.w` once, and Azahar doesn't keep it for later vertices. Writing it after each of the 8 `setemit` lines gave a correct SMW title screen on a control build (`93eaf83`), screenshot checked by me. Azahar's source not read. Saved as `tools/re/azahar-outpos-w.patch` and not applied to this branch, because the console doesn't appear to need it and the 8 extra instructions per tile are unmeasured there. |
| Small in-place fixes won't close the seams. | Recorded from the maintainer | Tried and failed per `CLAUDE.md`. The tile-overlap WIP was not carried over. |

| A small classifier on strip measurements can sort junk from fine. | **No, not with these measurements** | 2026-11-09. The maintainer labelled 100 crops from 96 games. After their own corrections that's 37 junk, 50 fine and 13 unsure. A logistic regression on 13 strip measurements caught 4 of 12 junk crops from held-out games and wrongly called 3 of 10 fine crops junk. With 4-fold cross-validation by game over 5 shuffles it was 54% accurate using all 13 measurements and 63% using colours-per-pixel alone, against 57% for always answering fine. The measurements describe a strip's shape and colours, not whether the game meant it to be seen. The labels do give the scorer's hit rate: junk on 8 of 14 crops from tied games, 15 of 35 from review games and 14 of 38 from shallow games, so about 4 in 10 flags are real. Two pairs of matching scenes got opposite labels, Yogi Bear (32/35) and Star Fox/Starwing (34/53). **The magenta in some crops is the games' own colour.** In Timon & Pumbaa every magenta pixel's layer value is 1, the backdrop, whose colour the game sets to magenta. Slam Masters' magenta is BG pixels that the flat picture hides. Both show only with depth: 1 px flat, 1 px at zero depth, and 160-700 px with depth. **Occlusion measurements**, the same day: for each flagged pixel, the layer maps say where its content came from. Backdrop means no layer drew there. Hidden means the eye's layer isn't within reach on that row of the flat picture. Same layer means the layer is nearby but in a new colour. Sprite means the pixel belongs to a sprite in the eye. On the maintainer's labels as they stood then (36 junk, 51 fine), cross-validated by game, occlusion alone was right 63% of the time against 59% for always answering fine. It wrongly called 8 of 51 fine crops junk, where the shape measurements called 19. Most flagged pixels in both classes are the same layer in a new colour. One narrow signal: a strip showing a layer absent from the whole flat row was junk on 9 of 12 crops, including Stunt Race FX, Slam Masters and both Madden dotted lines. Two of the 3 exceptions are one ACME title screen. It covers only 9 of 36 junk crops, and the rule was picked after seeing the data, so expect less on new crops. **Status: parked 2026-11-09 by the maintainer's decision.** No measurement here can decide presets by itself. The signal now only ranks the review list (`crop_labels.py rank`, which writes `review_ranked.md` in the pilot folder from up to 10 flagged frames per review game). The signal was widened to include the backdrop showing where the whole flat row keeps it covered, because the layer-only version ranked Timon & Pumbaa's magenta, the clearest junk in the library, last. On the labels the widened signal says junk on 19 crops, 13 of them junk and 6 fine, catching 13 of 36 junk. The backdrop part alone was 4 junk and 3 fine. Ranked first are Slam Masters, Doom, Biker Mice, Timon & Pumbaa, Madden 94 and Lethal Enforcers. Both Super Metroid entries rank last, which fits their rain being correct 3D. King Arthur's World and Dragon View rank low, which doesn't settle whether they're junk. |
